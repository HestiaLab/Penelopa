## 1. 背景与问题陈述

### 1.1 触发问题

对"多层嵌套图元在树中删除后撤销，Guid 是否改变"的追问，引出了对历史机制的完整审查：

- 当前实现中 Guid **不变**：`DocumentSnapshot` 持有图元对象引用，撤销时把同一实例重新挂回树；
- 但该保证依赖"快照恰好持有引用"，且快照是**全量状态复制**：按节点保存属性装箱值与容器子元素列表，撤销栈无容量上限；
- 量化结论：约 0.3–0.5 KB / 节点 / 快照，10,000 节点文档单步约 3–5 MB，100 步无界栈可达数百 MB；
- 每次编辑（即使只改一个属性）都按**文档规模**分配，且撤销/重做本身也捕获全量快照；
- 被删除的图元被子树引用保留在历史中，历史不清空则永不释放。

这不是一个孤立的性能问题，而是历史模型、写入边界、仿真预览与持久化四层耦合后的系统性缺陷。

### 1.2 现状能力与缺口

| 能力 | 现状 | 结论 |
| --- | --- | --- |
| 稳定身份 | `Primitive.Id` 构造时生成，加载时从文件恢复；删除后撤销恢复同一实例 | 已满足，需固化为不变量 |
| 事务边界 | 结构、对齐、属性、手势均经事务（`PrimitiveService` / `DocumentHistory`） | 已满足 |
| 选区语义 | 不捕获选区，恢复后仅保留存活项（SRS ED-F-035） | 现有产品决策，本轮需重新裁定 |
| 历史容量 | 无上限；全量快照 | **缺陷** |
| 历史范围 | 文档历史无界；仿真配置独立 50 步（SRS SIM-F-070/071） | **缺陷**：跨页面 Ctrl+Z 语义分裂 |
| 写入边界 | UI 已经由服务写入；但 `PropValue.Value`、`Container.AddChild/RemoveChild` 公开；仿真播放直接改模型 | **缺陷**：补丁记录可被绕过 |
| 扩展性 | 序列化按 .NET 类型名分发；渲染按类型 `switch`；属性值类型固定 | **缺陷**：无法支持白标/插件 |
| 持久化 | 显式 Save 写 localStorage；无自动保存、无崩溃恢复、无版本历史 | **缺陷**：商业化缺项 |
| 性能承诺 | 500 图元播放门禁；10,000 节点编辑体验未验证 | **缺陷**：无大数据量验收线 |

### 1.3 企业级对标

四种主流历史模型：

| 模型 | 代表产品 | 优点 | 代价 |
| --- | --- | --- | --- |
| 命令 + 逆命令 | AutoCAD、Office、Sketch、Godot | 内存 O(编辑量)，宏/脚本友好 | 每个命令两份实现，复杂结构逆算易错 |
| 差分补丁 + 结构共享 | tldraw、Excalidraw、Figma changeset | 内存 O(变更量)，可序列化、可协作 | 要求不可变模型或严格写入口 |
| 压缩全量快照 + 预算 | Blender（32 步）、Photoshop（50 状态） | 任意操作天然可逆、实现简单 | 内存与文档规模成正比，必须强预算 |
| 操作日志 / OT / CRDT | Google Docs、Figma 多人 | 实时协作唯一路线 | 撤销语义变为用户范围撤销，成本最高 |

企业级共同验收线：每文档单一历史、事务边界等于用户动作、内存有界、稳定 ID、结构操作可逆、选区/焦点恢复、历史与持久化解耦、命令可序列化。

### 1.4 约束

- 纯浏览器 Blazor WebAssembly，32 位线性内存；无后端（当前）；
- 文档上限：10,000 节点、深度 64、序列化 4 MiB（`DocumentSerializer`）；
- localStorage 单源约 5–10 MB 且同步阻塞，不适合自动保存；
- 运行时基线：.NET 10 LTS（P0 已完成，支持至 2028-11）；
- UI 依赖（P0 后）：SkiaSharp 4.154.0、Atlas.Blazor 0.4.0、Astrea.Components 0.9.0、ASP.NET Core 10.0.14。

| Q10 | 交付 | P0 .NET 10 LTS + 依赖验证 → P1 写入收口 → P2 补丁历史 → P3 统一历史 + overlay → P4 注册表 + v3 → P5 持久化 → P6 多文档会话；**v3-only，v1/v2 拒绝** |

开放项决议（2026-10-30 确认）：

1. **合并窗口：确认实施**——同一节点同一属性 800 ms 内连续编辑合并为一条，输入框失焦即提交；
2. **多文档预算：确认实施**——每文档 32 MB，全局最多同时打开 3 个文档会话；
3. **旧格式兼容：不保留**——产品处于预发布阶段，无市场存量用户；目标为 **v3-only**，v1 与 v2 均拒绝；导入回滚使用一次性状态（根与条目引用）；
4. **云后端：本期不实现**——只交付客户端契约（`baseRevision` 乐观锁、checkpoint 契约）；
5. **.NET 10：Atlas/Astrea 最新包已升级到 .NET 10**——P0 的依赖风险显著下降，仍须验证 SkiaSharp 与整体构建/性能；
6. **测试重写**：按阶段执行，新增不变量属性测试（随机操作序列 apply→undo→终态等价比对）。

## 3. 目标架构

### 3.1 模块与分层

```
┌──────────────────────── DocumentSession（每文档一个） ────────────────────────┐
│                                                                              │
│  DocumentModel            可变图元树，仅经受控 API 修改                          │
│      ▲                                                                       │
│  DocumentEditor           唯一写入口：事务、命令、记录器、标签                    │
│      │                                                                       │
│  PatchHistory             补丁条目、双预算、合并窗口、revision、导入一次性状态      │
│                                                                              │
│  SimulationRuntime        播放状态机 + Overlay（预览值，不写模型）                │
│                                                                              │
│  Registries               PrimitiveType / PropValue / Renderer / Command      │
│                                                                              │
│  Persistence              Serializer v3（v1/v2 拒绝）/ journal / 云同步契约        │
└──────────────────────────────────────────────────────────────────────────────┘
        ▲                                   ▲
   EffectiveValueSource                 DocumentState（只读快照 + 变更通知）
        │                                   │
   Penelopa.Rendering（绘制 / 命中 / 视口）   Penelopa.Web（面板 / 页面 / 互操作）
```

依赖方向保持单向：`Core ← Rendering ← Web`。`Core` 依旧不依赖 Blazor/SkiaSharp。

### 3.2 写入路径

```
UI / 命令 / 插件
   → DocumentEditor.Begin(commandId, label, parameters)
   → 受控变更 API（SetProperty / Add / Remove / Reparent / Group / Ungroup / SetConfig…）
   → Recorder 首次触碰属性时记录 before 值；结构操作即时记录
   → Commit：生成一个 HistoryEntry（无实际变化则丢弃）
   → Budget 裁剪 → revision++ → Changed(DocumentChange)
   → 触发渲染请求 / 自动保存防抖 / 云同步脏标记
```

- 所有持久变更必须经过 `DocumentEditor`；模型内部不允许存在第二条写路径；
- 手势（拖拽/缩放）在首次实际修改时开启事务，`PointerUp` 提交、`Escape`/取消精确回滚；
- 属性面板输入按"编辑会话"提交（失焦/回车），避免每次按键生成条目；
- 仿真配置编辑通过同一入口提交 `ConfigPatch`，不再维护独立撤销栈。

### 3.3 补丁契约

```csharp
public sealed record HistoryEntry(
    string CommandId,                          // 稳定命令 id，如 "penelopa.edit.setProperty"
    string Label,                              // 本地化键 + 参数，如 "Set Radius"
    IReadOnlyList<NodePatch> NodePatches,      // 文档补丁
    ConfigPatch? ConfigPatch,                  // 仿真配置补丁（不可变前后值）
    IReadOnlyList<Guid> SelectionBefore,       // 选区元数据（不入文档格式）
    IReadOnlyList<Guid> SelectionAfter,
    long Weight);                              // 预算估算权重（字节）

public sealed record NodePatch(
    Guid NodeId,
    IReadOnlyList<PropChange> Props,
    StructureChange? Structure);

public readonly record struct PropChange(
    string PropertyName,
    object? Before,
    object? After);

public enum StructureOp { Insert, Remove, Move }

public sealed record StructureChange(
    StructureOp Op,
    Guid NodeId,
    Guid? FromParentId,
    int FromIndex,
    Guid? ToParentId,
    int ToIndex,
    Primitive? Subtree);                       // Insert/Remove 时持有子树引用；Move 为 null

public sealed record ConfigPatch(
    SimulationConfig Before,
    SimulationConfig After);                   // 两侧均不可变，轨道实例可共享
```

关键语义：

- **正向应用顺序**：条目内按列表顺序应用；**逆向回滚顺序相反**；
- **索引快照**：`FromIndex/ToIndex` 是操作发生时刻的兄弟位置，回滚按该位置精确复位，保证根列表与容器子元素顺序；
- **子树引用而非序列化**：删除/插入条目持有 `Primitive` 引用，1 个节点约 8 B 引用 + 对象本身，序列化仅在导出或持久化时按需进行；
- **同一实例**：撤销与重做都复用条目中记录的实例，`Id` 不变；
- **配置不可变**：`SimulationConfig` / `SimulationTrack` 均为不可变记录，补丁只持有前后引用，未变更轨道天然共享。

### 3.4 事务、命令与合并

| 规则 | 定义 |
| --- | --- |
| 事务 | 可嵌套；最外层 Begin 开启记录，Commit 生成一条条目；嵌套共享最外层 |
| 无变化 | Commit 时记录为空则丢弃，不产生条目（沿用 ED-F-034） |
| 取消 | 逆向应用记录，恢复到事务前状态；不生成条目（手势取消） |
| 合并 | 键 = `(CommandId, NodeId, PropertyName)`；800 ms 窗口内连续编辑合并；结构操作、配置轨道增删、选区变化永不合并 |
| 标签 | 每条目携带 `CommandId` 与可读标签；UI 显示 "Undo: Set Radius" |
| 选区 | 选区变化本身不是历史条目；条目元数据记录前后选区，撤销/重做时恢复 |

### 3.5 预算与淘汰

估算权重公式（策略指标，不是精确堆测量）：

| 组成 | 权重 |
| --- | --- |
| 条目基础 | 256 B |
| 每个 `PropChange` | 200 B |
| 每个 `StructureChange` | 256 B |
| 条目保留的子树节点 | 512 B / 节点 |
| 选区 Guid（before + after） | 16 B / 项 |
| `ConfigPatch` | 512 B + 16 B × 轨道数 + 64 B × 关键帧数 |

规则：

- 默认 500 步 / 32 MB，任一阈值超出即从 undo 栈最旧端淘汰；
- redo 条目计入同一预算；提交新条目时清空 redo；
- 事务进行中不淘汰（避免淘汰尚未提交的上下文）；
- 导入回滚使用独立的一次性状态：保存根列表引用、选区引用与 undo/redo 条目列表，不复制图元，不计入 undo/redo 预算；持久编辑、配置变更、保存、加载或刷新后失效；
- 预算参数可配置（云端可下发），`CanUndo` / 当前深度 / 剩余预算对 UI 可见。

### 3.6 仿真覆盖层与生效值

现状（P3 已实现）：`SimulationRuntime` 把求值结果写入 `SimulationOverlay`，渲染、命中与读数读取生效值；`Stop()` 只清空 overlay。

目标：

```csharp
public interface IEffectiveValueSource
{
    float GetFloat(Primitive primitive, string propertyName); // 基础值 + overlay
    bool HasOverlay(Primitive primitive, string propertyName);
}
```

- `SimulationRuntime` 写入 `overlay: (Guid, string) → float`，不触碰模型；
- `Stop()` / 离开页面 / 组件销毁只清空 overlay，无需恢复；
- 渲染（`ScenePainter`）、命中测试、选举/包围盒、仿真读数与包围盒估算均可读取 `IEffectiveValueSource`；编辑画布未提供 overlay 时等价于基础值，仿真画布只读。
- 保存、序列化、历史、校验器只读取基础值；
- 崩溃或异常不会留下脏值——模型只含持久值；
- 预览期间禁止文档结构编辑；属性面板若可见，显示 overlay 值并标记为预览态，写入仍落基础值。

这与 SRS SIM-F-003 / SIM-F-034 的意图一致，且使实现真正满足"临时写入不得进入文档模型"。

### 3.7 持久化

#### 3.7.1 v3 文档格式

```json
{
  "Version": 3,
  "DocumentId": "9f6c…",
  "Revision": 42,
  "Primitives": [
    { "Id": "…", "Type": "penelopa.circle", "Props": { "Name": "Circle", "CenterX": 10 } }
  ],
  "SelectionIds": ["…"],
  "Simulation": { "Loop": false, "Tracks": [] },
  "Extensions": { "vendor.plugin": { "…": "保留原样" } }
}
```

- `type` 使用**稳定字符串 id**，不再使用 .NET 类型名；
- `documentId` 首次保存 v3 时生成；`revision` 由会话维护、云服务端校验；
- 未知**扩展段**原样保留（避免插件数据丢失）；未知**图元类型**拒绝加载并给出明确 id；
- `baseRevision` 是传输元数据，不写入文档内容；
- **v3-only（2026-10-30 确认）**：不保留 v1/v2 读取兼容；旧版本文件必须显式拒绝并提示该格式不再受支持。产品处于预发布阶段、无市场存量用户，因此不承担旧格式迁移成本；内置样例与附录语料在 P4 重新生成为 v3；

#### 3.7.2 自动保存与崩溃恢复

- 每个提交（或合并窗口关闭）后防抖 1.5 s 写入 IndexedDB：`{documentId, revision, savedAt, json, hash}`；
- 启动时比较 journal 与最近一次显式保存/云端同步的 revision，提示恢复文档；
- 恢复只恢复文档状态，不恢复 undo 栈；
- 显式保存成功后更新 journal 基线，云端保存成功后清理本地 journal。

#### 3.7.3 云端同步契约（客户端侧）

```
GET  /documents/{id}                  → 200 { json, revision, etag }
PUT  /documents/{id}  If-Match: etag  → 200 { revision, etag }
                                      → 409 { json, revision, etag }   // 冲突
POST /documents/{id}/checkpoints      → 201 { checkpointId }           // 命名版本
```

- 冲突 UI：重新加载（丢弃本地）/ 另存为副本 / 导出本地 JSON；
- 版本历史为服务端完整文档快照 + 名称，与 undo 解耦；
- 后端实现、鉴权、配额不在本 ADR 范围。

### 3.8 扩展注册表

| 注册表 | 职责 | 稳定标识 |
| --- | --- | --- |
| `PrimitiveTypeRegistry` | type id ↔ 工厂 ↔ 类型匹配（默认属性与领域校验由模型构造与校验逻辑承担） | `penelopa.circle`、`penelopa.rect`、`penelopa.triangle`、`penelopa.container.offset/rotation/flip` |
| `PropValueRegistry` | 属性值类型 ↔ 装箱/回读（序列化与历史） | 按 .NET 属性值类型注册 |
| `PrimitiveRendererRegistry` | type id ↔ `IPrimitiveRenderer` | 与 type id 相同 |
| `CommandRegistry` | 命令 id ↔ 可读名称（UI、宏与审计） | `penelopa.edit.setProperty`、`penelopa.structure.group`… |

规则：

- 核心 id 以 `penelopa.` 为前缀；第三方使用反向域名或厂商前缀（`acme.roundedRect`）；
- id 一经发布不可更改；重命名通过别名迁移表处理；
- 容器按 kind 拆分为独立 type id，避免"一个类型 + 枚举"在反序列化与注册表中的分支；
- 核心 type id：`penelopa.circle`、`penelopa.rect`、`penelopa.triangle`、`penelopa.container.offset`、`penelopa.container.rotation`、`penelopa.container.flip`；运行时不对 v1/v2 做类型映射。

### 3.9 多文档会话

- 每个文档一个 `DocumentSession`：模型 + 编辑器 + 历史 + 配置 + revision；
- 历史预算按文档独立计算；全局最多同时打开 3 个会话，超出提示关闭旧会话；
- 关闭会话丢弃 undo 栈；所有关闭会话（含空会话）进入文档库，含未保存内容时关闭前提示；journal 作为崩溃恢复副本，并用于重新打开关闭会话；
- 文档库、云列表、搜索属于产品层；P6 提供本地显式保存文档的最小重开库。
- P6 实现：UI 通过活动代理访问会话；每会话独立 localStorage/journal 键；`penelopa.activeSession` 保存活动描述，`penelopa.sessions` 保存打开会话集合，刷新后恢复全部标签与内容；显式保存文档写入 `penelopa.library` 供重新打开。

## 4. 关键不变量

| 编号 | 不变量 |
| --- | --- |
| I1 | 每一个持久变更都属于某条历史条目；不存在绕过记录器的写入 |
| I2 | 对任意条目：`Apply(Forward)` 后 `Apply(Inverse)` 恢复到逐字节等价的状态（含根顺序、容器子元素顺序、属性值） |
| I3 | 条目内正向按顺序应用、逆向按相反顺序应用，索引语义为操作时刻的兄弟位置 |
| I4 | 撤销/重做恢复**同一实例**；`Primitive.Id` 在删除→撤销、撤销→重做间保持不变 |
| I5 | 预算按公式估算并统一计入 undo + redo；淘汰只发生在提交/撤销/重做边界 |
| I6 | 选区是条目元数据，不属于文档状态；选区变化不产生条目 |
| I7 | 历史不写入文档、不跨会话；保存不清空历史；加载/替换文档重置会话历史 |
| I8 | Overlay 永不进入模型、历史、序列化、校验与保存负载 |
| I9 | 每次正向或逆向应用条目都是一次新 revision（供云同步与冲突检测） |
| I10 | 被删除子树由条目以引用持有；淘汰条目即释放，不存在其他隐藏引用 |

**I4 是原始问题的正式答案**：多层嵌套图元删除后撤销，Guid 不变；该保证被删除后撤销、撤销后重做、以及 SIM-F-082（Dormant 轨道恢复 Active）共同依赖。超过预算被淘汰的条目不再可撤销，其保留的 Guid 随条目释放。

## 5. 与现有 SRS 的冲突与修订结果

本 ADR 的若干决策**直接推翻原有需求**。以下修订已于 2026-10-30 落地到 SRS 2.0；概要设计与详细设计在对应阶段同步。

| 需求 | 原要点 | 修订结果（SRS 2.0） | 理由 | 阶段 |
| --- | --- | --- | --- | --- |
| ED-F-035 | 撤销/重做不得捕获或恢复选区 | 条目记录选区前后；撤销/重做恢复条目选区；选区变化本身不产生条目 | 商业化编辑器的共同预期；结构撤销后直接继续操作恢复的对象 | P2 |
| ED-F-036 | 快照必须包含根顺序、属性值、容器子元素顺序，不含选区与仿真配置 | 结果式不变量：条目必须能恢复根顺序、属性值、容器子元素顺序；可同时携带配置与选区元数据 | 机制从"快照"变为"补丁"，需求描述结果而非实现 | P2 |
| ED-F-063 | Undo import 恢复文档、选区、文档撤销栈、仿真配置与 Loop | 恢复统一会话状态（文档 + 配置 + 选区 + 统一历史） | 历史统一后不再有两套栈 | P2 |
| SIM-F-005 | 文档撤销/重做不得修改仿真配置 | 文档与配置共用一条历史；删除图元只使轨道 Dormant，撤销删除恢复 Active | 统一历史后撤销配置编辑是预期行为 | P3 |
| SIM-F-070 | 配置维护独立 50 步撤销栈 | 配置编辑进入统一历史，受统一预算约束 | 双栈语义分裂 | P3 |
| SIM-F-071 | 配置栈进入仿真页/加载时清空，不得与文档历史共享 | 重写为：配置编辑与文档共享统一历史，不得存在独立配置撤销栈 | 与 Q3 直接冲突 | P3 |
| SIM-F-072 | Preview/Paused/Finished 中配置撤销后立即按当前 `t` 重新求值 | 保留，改为"统一撤销/重做后立即重新求值" | 行为不变 | P3 |
| SIM-F-094 | 加载文档整体替换文档与配置并清空配置栈 | 加载重置整个会话（文档 + 配置 + 统一历史） | 语义一致化 | P3 |

SRS 2.0 同步新增的需求类别：

- 历史表示、预算与淘汰：记录型补丁、500 步 / 32 MB、可配置、UI 可预期；
- 历史条目标签与稳定命令 id；
- 统一历史跨页面顺序与选区恢复；
- Overlay：播放期间模型只含基础值，崩溃/中断不留脏值；
- **v3-only 格式**：v1/v2 拒绝，不保留只读兼容；
- 云同步乐观锁与冲突选择（客户端契约）；
- IndexedDB journal 自动保存与崩溃恢复提示；
- 注册表扩展：新增图元类型只改注册一处；
- 性能门禁：10k 节点延迟与内存指标。

## 9. 备选方案与不选理由

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 有界快照（500 步 / 32 MB，保留现有机制） | 备选，不采用 | 约一周工作量，能解决内存，但无法解决全量分配、双历史、扩展性与云同步；作为预算不足时的降级路线保留 |
| 语义命令 + 手写逆命令 | 不采用 | 宏能力更好，但每个命令两份实现，结构操作逆算长期易错；与现有任意属性直改风格冲突最大 |
| 不可变模型 + diff | 不采用（当前） | 为实时协作一步到位；但 Q1 无协作目标，WASM 下写时复制分配压力大，Core 全量重写性价比低 |
| 操作日志 / CRDT | 不采用 | 仅实时协作需要；撤销语义变为用户范围撤销，成本最高 |
| 全量事件溯源 | 不采用 | 加载慢、日志膨胀、迁移复杂，与 4 MiB 文档上限矛盾 |

- `PropValueRegistry`、`PrimitiveTypeRegistry`、`PrimitiveRendererRegistry` 改为并发字典/快照解析，避免并行测试注册自定义类型时与热路径读取竞争（覆盖率采集暴露并修复）。
