## 1. 目的与范围

本文档记录 Penelopa 从项目启动到当前交付基线的开发过程、阶段划分、质量保障、配置管理与风险管理。项目已处于可交付状态，因此本文档是**追溯编制**的现状基线，不是前期立项计划：不虚构角色分工、工时应答或审批记录，所有里程碑均以仓库提交历史为依据。

适用范围为仓库内的 Blazor WebAssembly 应用、核心模型与渲染库、测试套件及交付文档；不包含仓库之外的部署基础设施（GitHub Pages 由平台提供）。

## 2. 项目概述

Penelopa 是面向 Blazor WebAssembly 的图元对齐编辑器与关键帧仿真工作区。它在可停靠工作区中提供 SkiaSharp 画布、图元树、对齐工具与属性编辑器，并通过 `/simulation` 页面把 Float 属性编排为关键帧轨道，用于设计验证与调试。

| 项目 | 内容 |
| --- | --- |
| 代码仓库 | `HestiaLab/Penelopa`（MIT 许可） |
| 在线演示 | https://HestiaLab.github.io/Penelopa/ |
| 运行形态 | 纯浏览器静态应用，无后端服务 |
| 技术栈 | .NET 10 / Blazor WebAssembly / SkiaSharp 4.154.0 / Atlas.Blazor 0.4.0 / Astrea.Components 0.9.0 / TypeScript 5.9 |
| 测试栈 | xUnit 2.9.3、bUnit 2.13.3、Node `node:test`、Playwright（Chromium） |
| 文档格式 | v3 JSON（`.penelopa.json`，稳定 type id、DocumentId/Revision、Extensions）；v1/v2 拒绝 |

### 3.1 开发流程

1. 需求或缺陷先形成可验证的行为描述（仿真需求以编号条目管理）。
2. 在功能分支实现，核心逻辑优先落在无 UI 依赖的 `Penelopa.Core`，交互控制器与渲染分别落在 `Penelopa.Core.Interaction` 与 `Penelopa.Rendering`。
3. 同步补充单元、组件或端到端测试；必要时补充性能基准。
4. 本地执行构建、测试、格式与覆盖率门禁，提交拉取请求。
5. CI 在 Ubuntu 与 Windows 双平台构建测试，并单独执行格式、覆盖率、E2E 与依赖审计。
6. 通过评审后合并到 `main`；发布 GitHub Pages 为手动触发的显式动作。

### 3.2 组织与职责

本项目为单一维护者的开源项目，无外部团队分工。质量保障由自动化门禁承担，评审以拉取请求与代码审查报告为依据；不设专职测试、配置管理员或发布经理角色。

## 5. 质量保证

### 5.1 自动化门禁

CI 由五个作业组成：

| 作业 | 内容 |
| --- | --- |
| `build` | Ubuntu 与 Windows 双平台：`npm ci`、TypeScript 检查、JS 测试、生成 JS 漂移检查、锁定模式恢复、构建、.NET 测试 |
| `format` | `dotnet format --verify-no-changes` |
| `coverage` | 收集 XPlat 覆盖率并执行 `scripts/check-coverage.py` 门禁 |
| `e2e` | 安装 Chromium 并运行 Playwright 全量用例 |
| `audit` | 两个 npm 根目录的 `npm audit --audit-level=high`；NuGet 传递依赖审计，High/Critical 失败 |

覆盖率门禁为：`Penelopa.Core` 行覆盖率 ≥90%，`Penelopa.Rendering` ≥85%，`Simulation/` 与 `DocumentSerializer` 文件级 ≥90%。测试层级、缺陷分级与性能门槛见[软件测试规范](软件测试规范.md)。

### 5.2 评审与验证

- 代码审查覆盖架构、正确性、可访问性、性能与文档一致性；审查发现的问题按 P0–P3 分级整改。
- 仿真需求带编号与验收标准，实现后以测试追溯矩阵核对。
- 交付前在基线 `48cdf6d` 上全量重跑测试与性能基准，结果见[软件测试报告](软件测试报告.md)。

## 6. 配置管理

| 项目 | 规则 |
| --- | --- |

| 合并方式 | 拉取请求合并，提交信息带 PR 编号 |

| 发布 | GitHub Pages 工作流为 `workflow_dispatch`，不随 `main` 自动发布 |
| 交付基线 | 本次交付以提交 `48cdf6d` 为代码基线；交付文档版本 1.0 |

## 7. 发布与部署

发布产物为静态站点。GitHub Pages 工作流手动触发，发布时把 `<base href>` 改写为 `/Penelopa/`，并生成入口页的 `404.html` 副本，使 `/Penelopa/simulation` 等深链接进入 Blazor 路由而不是平台 404。应用不依赖服务器端接口；用户文档保存在 localStorage、IndexedDB journal 或本地文件中。

## 8. 风险管理与遗留项

| 风险 | 影响 | 现状与应对 |
| --- | --- | --- |
| 运行时升级已完成（P0） | 后续安全更新与工具链寿命 | 已升级到 .NET 10 LTS（支持至 2028-11）；后续随 .NET 版本升级评估 WASM 资源与测试栈 |
| SkiaSharp 4 迁移 | API 与原生资源变化 | 已迁移到 4.154.0，完成 `SKPathBuilder`、`SKFont`、`SKSamplingOptions` 等 API 适配；WASM 原生链接已通过 |
| AngleSharp 测试依赖 | 仅测试环境 DOM 解析 | bUnit 2.13.3 / AngleSharp 1.8.6；测试栈已迁移，依赖审计由 CI 持续验证 |
| v3 格式迁移 | v1/v2 不再兼容 | 已完成：v3-only，内置样例与附录语料已迁移；旧格式拒绝并提示 |
| E2E 仅覆盖 Chromium | 其他浏览器行为未自动验证 | 目标为支持 WebAssembly 与 WebGL 的现代桌面浏览器；跨浏览器验证为手工事项 |
| 性能基准环境敏感 | 门槛可能随机器波动 | 基准仅在 `PERF=1` 运行，分别记录 tick、.NET frame 与 paint；门禁阈值留有余量 |
| 文档规模上限 | 4 MiB、10000 节点、深度 64 | 超限拒绝并保留当前文档；适合单场景编辑，不适合超大场景 |
| 仅浏览器本地存储 | 换设备/清缓存即丢失 | 提供文件导入/导出、单槽备份与 per-session journal；云同步契约已定义但生产后端待选型 |
| 可访问性验证以自动化为准 | 屏幕阅读器组合未系统覆盖 | 键盘路径、ARIA 与焦点管理纳入测试；发布前保留手工检查项 |
| 过程文档缺失 | 决策背景不可追溯 | 已建立架构决策记录（ADR-001）；后续重构决策按 ADR 维护 |
